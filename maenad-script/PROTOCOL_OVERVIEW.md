# Maenad Protocol: Technical Workflow Overview

This document provides a detailed, technical description of the Maenad protocol for decentralized asset sales, based on the project's Solidity contracts and Rust scripts.

## Core Components

-   **`ExchangeChannel.sol`**: The primary smart contract deployed by the Seller, orchestrating the entire sale lifecycle.
-   **`VDD.sol` / `VSS.sol`**: Base contracts providing verification logic for ZK proofs.
-   **Seller**: The entity listing an asset for sale. Owns a master secret `dataKey`.
-   **Buyer (Audience)**: An entity purchasing the asset.
-   **ZK Proofs**:
    -   **VSS (Verifiable Secret Sharing)**: A proof that the Seller has correctly encrypted their `dataKey` for a specific Buyer.
    -   **VDD (Verifiable Data Decryption)**: A proof that an encrypted asset on a public storage network corresponds to the original, publicly committed asset ID.

## Protocol Stages

### Stage 1: Listing (`listFile`)

1.  **Objective**: A Seller lists a digital asset for sale.
2.  **Off-Chain (Seller Script)**:
    -   An `original_asset_id` (`bytes32`) is computed from the raw asset data. This is the canonical identifier for the asset.
    -   A `saleId` (`bytes32`) is pre-calculated based on the channel's address, the current chain ID, and the contract's current `nonce`.
3.  **On-Chain (Seller Transaction)**:
    -   The Seller calls `listFile(DataCommitment memory _commitment, ...)` on the `ExchangeChannel` contract.
    -   The `_commitment.data` field contains the `original_asset_id`.
4.  **Contract Logic (`ExchangeChannel.sol` & `VDD.sol`)**:
    -   The contract MUST compute the exact same `saleId` using `getNextSaleId()`, which is `keccak256(abi.encodePacked(address(this), block.chainid, nonce))`.
    -   The nonce is incremented.
    -   A `data_id` is generated by calling the internal `_listDataInfo`, which in turn calls `getDataId(_commitment.data)`.
    -   `getDataId` is a `pure` function defined as `keccak256(dataCommitment)`. Therefore, `data_id = keccak256(original_asset_id)`.
    -   This `data_id` is stored on-chain in the mapping `saleVersions[saleId]`. This `data_id` is the official **version** for this sale.

### Stage 2: Purchase (`purchase`)

1.  **Objective**: A Buyer pays to acquire the rights to the asset.
2.  **Off-Chain (Buyer Script)**:
    -   The Buyer generates a temporary secret (`secret_sharing_key`).
    -   A commitment, `vssKeyCommitment` (`bytes32`), is calculated from this secret (e.g., `blake3::hash(secret_sharing_key)`).
    -   The Buyer reads the Seller's public key from the contract.
    -   The Buyer encrypts their `secret_sharing_key` using the Seller's public key (ECIES). This yields an `encryptedVssKey` and an ephemeral public key, `eph_pk`.
3.  **On-Chain (Buyer Transaction)**:
    -   The Buyer calls `purchase(...)`, providing payment.
    -   **`saleId`**: The ID for the specific sale.
    -   **`dataVersion`**: A `bytes32` value intended to match the `data_id` stored on-chain. The script provides `keccak256(original_asset_id)`.
    -   **`dataCommitment`**: The `eph_pk` (`bytes`) from the ECIES encryption. This is required by the seller later for decryption.
    -   **`vssKeyCommitment`**: The `bytes32` commitment to the buyer's secret.
    -   **`encryptedVssKey`**: The `bytes32` encrypted buyer's secret.
4.  **Contract Logic (`ExchangeChannel.sol`)**:
    -   The first operation is `require(dataVersion == saleVersions[saleId], "Wrong data version")`. This check validates that the buyer is purchasing the correct, listed version of the data. **This is the point of failure.**
    -   If successful, the contract locks the buyer's funds and stores their VSS-related information.

### Stage 3: Fulfillment (`fulfill`)

1.  **Objective**: The Seller provides the ZK proofs required to release the asset key to the buyer.
2.  **Off-Chain (Seller Script)**:
    -   The Seller retrieves the `PurchaseEvent` to get the `encryptedVssKey` and `dataCommitment` (`eph_pk`).
    -   The Seller decrypts the `encryptedVssKey` to get the Buyer's `secret_sharing_key`.
    -   The Seller generates a **VSS Proof**, proving they correctly used the `secret_sharing_key` to wrap their master `dataKey`.
    -   The Seller generates a **VDD Proof**, proving the integrity of the encrypted asset stored externally.
3.  **On-Chain (Seller Transaction)**:
    -   The Seller calls `fulfill`, submitting the `VSSArgs` (containing the wrapped `dataKey` and VSS proof) and `VDDArgs`.
4.  **Contract Logic**:
    -   The contract calls `shareDataKey` which verifies the VSS proof. If valid, the buyer is now considered `isPrivy` (has the key).
    -   The contract calls `submitVDDProof` which verifies the VDD proof.

### Stage 4: Settlement (`settle`)

1.  **Objective**: The Seller receives payment.
2.  **On-Chain (Anyone can call)**:
    -   `settle` can be called once the buyer is privy, the VDD proof is verified, and an Oracle has confirmed the data is available.
    -   The contract transfers the locked funds from the buyer to the seller.

## Analysis of "Wrong data version" Error

The `purchase` function fails because `dataVersion != saleVersions[saleId]`.

-   `saleVersions[saleId]` is set during `listFile` to be `keccak256(original_asset_id)`.
-   `dataVersion` is passed from the Rust script as `keccak256(original_asset_id)`.
-   `saleId` must be identical between the off-chain script and the on-chain contract.

The root cause is a mismatch in the calculation of `saleId`. The Rust script was encoding the `chain_id` as a 4-byte `u32`, while the Solidity contract encodes it as a 32-byte `uint256` as part of `abi.encodePacked`. This results in two different `saleId` hashes, causing the `purchase` function to look up an invalid entry in the `saleVersions` mapping, which in turn causes the version check to fail.
