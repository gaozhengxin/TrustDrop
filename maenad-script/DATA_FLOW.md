# Maenad Protocol: Data & Trust Flow

This document outlines the end-to-end data flow of the Maenad protocol, clarifying the roles of participants, the location of data processing, and the visibility of key information at each stage.

## Core Concepts

*   **Actors**:
    *   **Seller**: The user selling access to digital data.
    *   **Buyer**: The user purchasing access to the data.
*   **Execution Environments**:
    *   **Local**: The user's own machine running the script. All private keys and raw data are handled here.
    *   **On-Chain**: The Arbitrum Sepolia blockchain where the smart contracts (`ExchangeHub`, `ExchangeChannel`) live. This is the public, verifiable source of truth.
    *   **SP1 ZKVM**: A decentralized network for generating Zero-Knowledge proofs. It receives private inputs but only outputs a public proof and public values.
    *   **Walrus**: A decentralized storage network for holding large data blobs (like the encrypted asset).

---

## Stage 1: Asset Listing

The Seller prepares the data and lists it for sale on the blockchain.

| Action | Actor | Location | Data Involved | Visibility / Notes |
| :--- | :--- | :--- | :--- | :--- |
| **1. Read Raw Asset** | Seller | Local | `raw_asset_data` | **Private**. Stays on the Seller's machine. |
| **2. Generate Asset Key** | Seller | Local | `asset_encryption_key` | **Private**. This is the master key for the data. For this script, it's hardcoded as `[0x22; 32]`. |
| **3. Encrypt Asset** | Seller | Local | `encrypted_asset_data` | **Private (at this moment)**. Generated by ChaCha8 encrypting `raw_asset_data` with `asset_encryption_key`. |
| **4. Calculate Commitments** | Seller | Local | `original_asset_id` (ID of raw data)<br>`encrypted_blob_id` (ID of encrypted data) | **Public**. These are `compute_rs_id` hashes. They commit to the data without revealing it. |
| **5. Upload to Storage**| Seller | Local -> Walrus | `encrypted_asset_data` -> `walrus_blob_id` | `encrypted_asset_data` is sent to the network. The data itself is **Publicly Accessible** on Walrus, but opaque without the key. |
| **6. Create/Get Channel**| Seller | Local -> On-Chain | `channel_address` | **Public**. A new `ExchangeChannel` contract is created on-chain for the Seller. |
| **7. List on Channel** | Seller | Local -> On-Chain | `original_asset_id`<br>`price` (e.g., 0.01 ETH) | **Public**. The `listFile` function is called, creating a public record of the sale offer. |

## Stage 1.5: Data Key Commitment

The Seller commits to the master asset key on-chain. This is crucial for later ZK proofs.

| Action | Actor | Location | Data Involved | Visibility / Notes |
| :--- | :--- | :--- | :--- | :--- |
| **1. Hash Asset Key** | Seller | Local | `data_key_commitment` | **Public**. Calculated as `Sha256::digest(&asset_encryption_key)`. |
| **2. Submit Commitment**| Seller | Local -> On-Chain | `data_key_commitment` | **Public**. Stored in the `ExchangeChannel` contract. This links all future proofs to this specific key. |

---

## Stage 2: Purchase

The Buyer discovers the listing and pays to initiate the exchange.

| Action | Actor | Location | Data Involved | Visibility / Notes |
| :--- | :--- | :--- | :--- | :--- |
| **1. Derive Sharing Key**| Buyer | Local | `secret_sharing_key` | **Private**. Derived from the `original_asset_id`. This key is unique to this buyer for this specific sale. |
| **2. Commit to Sharing Key**| Buyer | Local | `vss_key_commitment` | **Public**. Calculated as `Sha256::digest(&secret_sharing_key)`. Commits to the key without revealing it. |
| **3. Encrypt Sharing Key**| Buyer | Local | `encrypted_vss_key`<br>`eph_pk` (ephemeral pubkey) | **Public**. The `secret_sharing_key` is encrypted using ECIES for the Seller. The result is sent on-chain. |
| **4. Call `purchase`** | Buyer | Local -> On-Chain | `unique_sale_id`<br>`vss_key_commitment`<br>`encrypted_vss_key`<br>`eph_pk`<br>Value: `price` | **Public**. The buyer pays and records their intent to buy, along with their key commitments and encrypted key. |

---

## Stage 3: Fulfillment (The ZK-Proof "Magic")

The Seller sees the purchase and generates proofs to securely release the key to the Buyer.

| Action | Actor | Location | Data Involved | Visibility / Notes |
| :--- | :--- | :--- | :--- | :--- |
| **1. Get Buyer Info** | Seller | Local <- On-Chain | `encrypted_vss_key`, `eph_pk` | **Public**. Seller reads the Buyer's info from the `PurchaseEvent` log. |
| **2. Decrypt Sharing Key**| Seller | Local | `secret_sharing_key` | **Private**. Seller uses their `owner_sk_bytes` (ECIES private key) to decrypt the Buyer's `secret_sharing_key`. |
| **3. Wrap Asset Key** | Seller | Local | `wrapped_asset_key` | **Private (at this moment)**. Seller encrypts `asset_encryption_key` with the Buyer's `secret_sharing_key`. This is the package for the buyer. |
| **4. **Generate VSS Proof** | Seller | Local -> SP1 ZKVM | **Inputs (Private)**:<br>`asset_encryption_key`<br>`secret_sharing_key`<br><br>**Output (Public)**:<br>`vss_proof`, `vss_public_values` | Proves that `wrapped_asset_key` was created correctly. The ZKVM sees the private keys but only outputs a public proof. |
| **5. **Generate VDD Proof** | Seller | Local -> SP1 ZKVM | **Inputs (Private)**:<br>`asset_encryption_key`<br>`raw_asset_data`<br><br>**Output (Public)**:<br>`vdd_proof`, `vdd_public_values` | Proves that the `encrypted_asset_data` on Walrus is the correct encryption of `raw_asset_data`. |
| **6. Call `fulfill`** | Seller | Local -> On-Chain | `vss_proof`, `vdd_proof`<br>`wrapped_asset_key` | **Public**. The Seller submits the two ZK proofs and the wrapped key to the `fulfill` function. The contract verifies both proofs. |

---

## Stage 4 & 5: Settlement & Recovery

The final steps where money changes hands and the Buyer gets the data.

| Action | Actor | Location | Data Involved | Visibility / Notes |
| :--- | :--- | :--- | :--- | :--- |
| **1. Oracle Verification**| Automated | On-Chain <-> Walrus | `encrypted_blob_id` | **Public**. An oracle service checks Walrus to confirm the data is available and updates the contract state. |
| **2. Settle Funds** | Seller | Local -> On-Chain | - | **Public**. Seller calls `settle` after oracle success. The contract releases the Buyer's payment to the Seller. |
| **3. Get Wrapped Key** | Buyer | Local <- On-Chain | `wrapped_asset_key` | **Public**. Buyer listens for the `DataKeyShared` event (from `fulfill` step) to get their `wrapped_asset_key`. |
| **4. Unwrap Asset Key**| Buyer | Local | `asset_encryption_key` | **Private**. Buyer uses their `secret_sharing_key` to decrypt the `wrapped_asset_key` and recover the master key. |
| **5. Download & Decrypt**| Buyer | Local <- Walrus | `encrypted_asset_data` -> `raw_asset_data` | **Private**. Buyer downloads the data from Walrus and uses the recovered `asset_encryption_key` to decrypt it. |
